The Discipline

⚙️ Graph Engineering

The practice of designing, building, and operating graph-powered systems at enterprise scale
📖
What is it
The engineering discipline that spans the entire graph pipeline — from modeling the domain ontology, to constructing and indexing the knowledge graph, to optimizing Cypher queries for context extraction, to orchestrating deterministic decision logic. It's not a layer you add; it's the craft that makes every layer work.
❓
Why it matters now
2026 is the "Accountability Era" for graph technologies. With GraphRAG, agentic AI, and enterprise knowledge graphs going mainstream, organizations need engineers who don't just query graphs — they architect them for performance, governance, explainability, and AI-readiness.

The Four Pillars of Graph Engineering

📐
Graph Data Modeling
Designing the ontology — node labels, relationship types, property schemas, constraints. Getting this wrong means every downstream query is fragile.
🔧
Graph Construction
ETL pipelines, entity resolution, seeding, indexing, and validation gates. The "soul-crushing" work of building a clean, production-quality graph.
⚡
Query & Feature Engineering
Writing and optimizing Cypher traversals to extract features from graph topology — the context graph extractors that power real-time decisions.
🔄
Decision Orchestration
Wiring graph outputs to deterministic rules, confidence blending, precedent matching, and persisting decisions back to enrich the graph.
→ Outcome: An engineering practice that transforms a graph database from a data store into a decision intelligence platform — scalable, auditable, and AI-ready.
The Four Layers

What Graph Engineering Builds

Each layer feeds the next. Together, they form the architecture of a graph-powered decision system.

Layer 01

🧬 Ontology

The blueprint — before a single record is stored
📖
What is it
A formal definition of every entity type (Person, Account, Device, Policy…) and every relationship type (OWNS, VIEWED, FILED_CLAIM…) that can exist in your domain.
❓
Why it matters
Without it, data is noise. The ontology ensures engineering, business, and compliance all describe the same world the same way.

Layer 02

🗄️ Knowledge Graph

The facts — the ontology filled with real data
📖
What is it
Real people, real accounts, real transactions — all stored as connected nodes and edges in Neo4j. Decisions are stored back, so the graph grows smarter over time.
❓
Why it matters
Relationships are first-class citizens, not buried in JOIN tables. Questions like "who shares a device with a fraudster?" are a single traversal, not a 4-table join.

Layer 03

🔍 Context Graph

The focus — only what matters for this decision
📖
What is it
A focused subgraph extracted at the moment of decision. Out of 56K nodes, Cypher traversals pull the 15–30 relevant to this customer and this event, transforming topology into measurable features.
❓
Why it matters
This is where the audit trail lives. It preserves the exact state of the world at decision time — three weeks later, you can see exactly what data the engine saw.

Layer 04

🎯 Next Best Action

The decision — rules applied, action recommended
📖
What is it
Deterministic rules applied to context graph features, producing: a recommended action, confidence score, ranked alternatives, counter-offers, and a plain-English narrative. The LLM never decides — it only explains.
❓
Why it matters
Every decision is traceable (links to policies + context), negotiable (counter-offers), and persistent — written back into the graph, completing the feedback loop.

→ Outcome: A justified, auditable action that enriches the graph and completes the feedback loop.
Live Example

Robert Vance — "The Sad User"

A customer who browsed, calculated financing, test-drove a car… but never bought. Watch all five concepts in action.

⚙️

Graph Engineering designed the system

A graph engineer modeled the omnichannel domain (web sessions, mobile engagement, physical visits), built Cypher extractors for each channel, optimized indexes for sub-second traversal, and orchestrated the decision pipeline to persist every action back into Neo4j.

🧬

Ontology defines the entities

The system knows that a Person can INITIATE a Session, VIEW a BrowsedVehicle, ENGAGE_WITH a FinancingCalculator, and TAKE_TEST_DRIVE at a Dealership.

🗄️

Knowledge Graph stores Robert's world

Robert Vance exists in Neo4j with real data across three channels:

🌐 Web: 4 views of Audi A4 (20 min browsing)
📱 Mobile: 72-month financing calculator at 4.99% APR
🏢 Physical: 90-min test drive at Central Audi Manhattan
❌ Result: No purchase recorded
🔍

Context Graph extracts omnichannel signal

The engine traverses Session → BrowsedVehicle, Session → FinancingCalculator, and Person → PhysicalVisit → Dealership to extract:

view_count: 4  |  used_calculator: true
test_drive_count: 1  |  has_purchased: false

No single channel tells this story. The context graph synthesizes all three.

🎯

Next Best Action fires

Rule POL-MAR-01 (Omnichannel Abandonment Recovery) matches: 4+ views + calculator + 1+ test drives.

📲 Send Conversion SMS — Locked APR for 48h — 98% confidence

"The system KNOWS he took a test drive because of the graph relationship, not because an AI guessed."
